# 翻译流程

文译先理解全书，再按章翻译并保存已完成工作，最后审校和导出。本页说明影响质量、
时间、费用及恢复的流程选择。命令见 [CLI 指南](cli.md)，选项见
[配置参考](../reference/configuration.md)，输入保留能力和导出限制见
[格式参考](../reference/formats.md)。

<a id="overview"></a>

## 默认流程

1. 解析并保存原文。
2. 准备章节梗概、文风指导和全书概览。
3. 翻译并润色章节，对齐格式，更新术语库。
4. 审校全书，开启 Autofix 时发布修订。
5. 导出已保存译文。

默认使用标准翻译，并开启全书理解、润色、注释对齐、最终 Review 和
**Autofix 发布**。三稿精翻和增量术语备注需要主动开启。
默认只导出单语版，双语版可选。

<a id="quality-and-cost"></a>

### 质量与费用取舍

| 选择 | 作用 | 成本或限制 |
| --- | --- | --- |
| 全书理解 | 第一批正文翻译前具备章节事实和全书背景 | 扫描全部章节原文，长章节需要多次预扫请求 |
| 润色 | 再次改善目标语言表达 | 标准批次通常增加一次模型请求；流畅不等于忠实 |
| 三稿精翻 | 三份独立尝试后，对照原文综合润色 | 正文阶段通常调用四次，标准翻译加润色为两次 |
| 注释／样式对齐 | 在译文中恢复链接和混合格式的位置 | 局部范围可能增加模型请求，不确定位置按格式降级 |
| Review 与 Autofix | 检查全书一致性、取证并修订 | 可能多轮审校并调用 Fixer；发布会改变正式译文 |
| 更多上下文或术语证据 | 提供跨段证据 | 提示词更长；生产术语证据还需额外请求 |

关闭某阶段会减少该阶段工作，但总费用不会必然按固定比例下降。
重试、输出长度、推理 token 和 provider 定价都会影响成本。
复用提示词前缀可能有利于服务端缓存，但不保证命中。
这些选项都不保证译文更准确；请比较代表性段落，并亲自检查重要结果。

<a id="reasoning-effort"></a>

### 各阶段推理强度

在推理模型上，隐藏的思考 token 往往占输出费用和耗时的主要部分。你可以在 `llm.routes`
中按操作覆盖 `thinking`（见[连接、模型配置与路由](../reference/configuration.md#model-profiles)）：

| 操作 | 推荐设置 | 取舍说明 |
| --- | --- | --- |
| `translation.body` | `nextgen`（`polish_mode: sparse`）下可用 `thinking: "off"`；不开启稀疏润色时建议保留推理 | 在 DeepSeek V4.1 Flash 的 `nextgen` 对照测试中，关闭正文翻译推理使正文输出 token 减少约 71%，经稀疏润色后的盲评质量与 `high` 基本持平（`8.35` 对 `8.40` / 10）。 |
| `glossary.align_history` | `thinking: "off"` | 输入很小的历史对齐调用；关闭推理使输出 token 减少约 85%、速度快约 3 倍，且结果完全一致。 |
| `glossary.extract` | 保持 `thinking: low`（**不要**关闭） | 足以稳定识别人名地名，耗时远低于 `high`。完全关闭在 `incremental` 模式下容易误判称谓映射；在 `compiled`（Book Bible）模式下更会放行普通词与残片噪声，进而触发大量误报 `glossary_miss` 并使润色升档次数增至 3 倍，反倒抵消节省。 |
| `polish.body` | `polish_mode: sparse` 下设为 `thinking: low` | 常规批次保持低成本，同时让风险路由 `thinking_boost` 在命中高严重度告警，或同时达到古文密集与对话密集阈值时自动升档。 |

在 YAML 中请给 `"off"` 加引号（避免被解析为布尔值 `false`），且关闭 `translation.body` 推理时需同时启用稀疏润色：

```yaml
pipeline:
  polish: true
  polish_mode: sparse

llm:
  routes:
    translation.body: {model: deepseek/deepseek-flash, thinking: "off"}
    polish.body: {model: deepseek/deepseek-flash, thinking: low}
    glossary.extract: {model: deepseek/deepseek-flash, thinking: low}
    glossary.align_history: {model: deepseek/deepseek-flash, thinking: "off"}
```

具体节省幅度与质量表现因模型家族和语言对而异；用于整本书前建议先抽查几章对比。

<a id="preparation"></a>

## 翻译前的准备

解析不调用翻译模型，只识别章节和段落。`wenyi parse` 以及 Web/Desktop 上传解析
会保存只读的[原文快照](../reference/formats.md#source-snapshots)。
PDF 解析仍可能需要 MinerU 或 BabelDOC 服务。仅解析不代表翻译状态初始化完成。

`prepare` 或 `translate` 开头的准备阶段依次执行：

1. 当 `language.source` 为 `auto` 时识别原文语言；显式指定语言可跳过这次请求。
2. 开启 `pipeline.book_understanding: true` 时，概括**每章完整原文**，
   长章节按有界分块处理。
3. 以开头、中间、结尾的原文样本分析文风和人物语气，章节梗概提供事实背景。
4. 根据文风指导和章节梗概生成全书概览。

准备阶段**不翻译正文，也不抽取术语**。已有项目术语和导入映射会保留。
关闭全书理解只跳过章节梗概与全书概览，不关闭文风分析。

开启全书理解后，有文本的章节必须具备可用梗概才能开始正文翻译。
章节梗概失败会停止准备；全书概览失败则记录警告，允许依靠章节梗概继续翻译。
成功的整章梗概和文风分析可在身份匹配的重试中复用；
尚未完成的单章内部不逐块保存预扫检查点。

<a id="context-and-glossary"></a>

## 翻译上下文与术语库

章节和正文批次按原文顺序推进。常规批次获得文风指导、全书概览、
**当前术语库**（全量或本批相关，见下文）、本章梗概、相关原文注释、最近译文、待译原文，以及一个后续原文片段作为只读参考。
后文参考帮助保持连贯，但不得提前翻译，也不计入当前输出段数。

最近译文从已保存的正式译文重建，可跨越前章。
`pipeline.rolling_context_tokens` 默认 512 token。
优先保留完整的最近段落；最近一段单独超限时只取其尾部。
预算设为零只关闭前文译文，不关闭后文原文参考。
BabelDOC 另有[按版面角色约束的上下文边界](../reference/formats.md#babeldoc)。

<a id="deferred-polishing"></a>

标准模式下 `pipeline.polish_concurrency` 大于 1 时，润色不再阻塞翻译：初稿保存后进入润色队列，
下一批立即开始。最近译文上下文和术语抽取始终读取未润色初稿，结果不随润色完成时间变化，
以少量连贯性换取慢速润色模型下的吞吐。章节的全部润色任务应用后才标记为完成，注释对齐基于润色后的译文。
润色失败或返回段数不符时保留初稿作为译文，并记录 `batch_polish_failed` 事件。
中断后续跑会重新润色已保存的初稿，不重新翻译。

常规术语抽取（`pipeline.glossary_mode: incremental`）从已完成的原译文对开始。因此，没有导入术语时，第一批正文没有预定映射。
新术语及冲突影响后续批次，不自动改写早先译文。
每批的术语抽取与下一批的翻译同时进行，所以新词条从再下一批开始生效；下一批仍能在近期译文上下文中看到上一批的译法。
章节在其术语保存后才标记为完成。
术语库是名称映射的权威来源；文风指导保留原文身份和人物描述。

将 `pipeline.glossary_mode` 设为 `compiled` 时，文译会改为在第一章翻译前根据章节摘要与原文挖掘高频实体，通过双语境熵探测与全局裁定编译冻结的 Book Bible，从而跳过热路径上的逐批与章末抽取（消除一批延迟，并启用大于 1 的 `pipeline.chapter_concurrency`）。用户导入或手动编辑的词条保持不变。

默认（`pipeline.batch_glossary: all`）每个待译正文批次接收全部当前实体映射，而新写入的 EPUB 目录标题（`navigation`）仅在命中当前请求原文时才携带（旧版以 `term` 存储目录标题的存量项目会在 Review 中自动获得同等过滤）。
设为 `batch_glossary: relevant` 时，每批只接收原文或别名出现在本批原文段落、后续原文参考、
注释上下文或章节摘要中的词条；术语抽取也只看到在被抽取文本中出现的已有词条。
长篇书籍的完整术语表每次请求可能达到数万 token，因此长篇更适合 `relevant`。
`pipeline.glossary_prompt_tokens` 是可选上限，默认 `0` 表示不设上限。设置后，`all` 保留上限内追加稳定的前导词条
（利于前缀缓存复用）并附加命中本批的后续词条，`relevant` 只发送上限内的命中词条。
发送请求前，文译还会按模型的 `context_window` 估算提示词与输出预留总量，超限时自动缩减术语表或给出可执行报错。
只用代词或称号指代人物的段落此时依靠章节摘要和近期译文获得映射。
新的 Reviewer 请求接收最终全量实体术语库以及命中当前审校分块的 EPUB 目录标题，并按审校模型的 `context_window` 自动裁剪（多段分块仍超限时自动二分拆分）；取证查询和单段 Fixer 可使用相关子集。
每条 `batch_translated` 事件记录所发送的词条数（`glossary_terms`）及术语块 `cl100k_base` 词元数估计（`glossary_tokens`）。

因此术语抽取保持精简：只收人名地名等专名、本书特有术语、反复出现的称谓和固定表达，
不收日常词汇、一次性描述或单句台词。Wenyi 还会在模型之外强制执行这一点：原文在全书只出现一次的新词条不入库；
中文原文中随说话人和听话人而变的自称与称谓（如孤、本王、大人、公子）以及单字普通词也不入库，单字专名（如蜀）保留。
抽取到的译法若与已存译名只差大小写、空格、开头的 “the” 或句末标点，不记为冲突；术语导入和手动编辑仍精确比较译名。

另有两项检查不依赖原文语言的词表。译入英语时，译名只由代词和称号词构成（“I”“your son”“Your Excellency”）的抽取词条不入库；
“Lord Jiang” 含有名字，予以保留。翻译过程中，若成品译文反复不采用某个抽取词条，它会从之后的正文翻译和润色提示词中省去。
计数从按全书顺序最早采用已存译名的初稿段落开始，因此在全书中位于修正译名首次被采用之前的段落不计入；
此后其原文出现在至少五个段落中、而采用该译名的不到 35% 时即省去。该词条仍保留在术语库中；你导入、添加、编辑或裁定过的词条始终发送。
每次变化记录一条 `glossary_terms_left_out` 事件。译名按原样匹配，因此在名词有屈折变化的目标语言中
（俄语 “Лондон” 写作 “Лондоне”），即使译者遵循了词条，它仍可能被省去。

抽取在每批之后和每章结束时运行。DeepSeek 预设以 `thinking: low` 运行 `glossary.extract`：
从已完成译文中识别名称，低强度已足够，耗时远少于高强度。
各阶段推理强度建议及为何不应关闭 `glossary.extract` 的推理，见[各阶段推理强度](#reasoning-effort)。

EPUB 正文翻译完成后，Wenyi 补齐解析出的导航树译文，并在最终 Review 前将其原译文对收入术语库，
包括嵌套条目、复用的标题和先前已保存的标题。已有术语译名保持不变，不同的导航译名记为待处理冲突。
Review 据此检查正文章首、书内可见目录和行文中的差异；修订写回正式译文需要开启 Autofix。
关闭 Review 时仍保存导航术语，但此步骤不会在导出时同步改写正文或可见目录。

译前不做人物发现或全书取证。普通术语抽取在译后进行；需要逐词维护有出处的事实时，可开启 [CLI 增量术语备注](cli.md#terminology-context)。

<a id="three-draft-precision"></a>

## 三稿精翻

`pipeline.translation_mode: three_draft_synthesis` 表示**三份独立初稿后，再做一次对照原文的综合润色**，
不是从三稿中选出胜者。该模式必须开启润色。

```text
同一份冻结原文与上下文
  ├─ 独立初稿 T1 ─┐
  ├─ 独立初稿 T2 ─┼─ 对照原文综合润色 → 最终译文
  └─ 独立初稿 T3 ─┘
```

三份初稿并发生成，互不可见。综合润色把它们作为可能有误的资料，优先遵循原文并融合有用部分，
没有独立的准确性裁判。保存的润色前对照是 T1，不是被认定最准确的初稿。

普通批次调用三次初稿生成和一次综合润色；
标准翻译加润色则各调用一次。两种模式使用相同的模型路由和输出上限。
四次与两次调用**不等于费用固定翻倍**：输入规模、输出 token、重试以及全书其他阶段仍要计费。

若初稿或综合润色在配置的重试次数内仍无法产生可用结果，当前批次会停止，
不会悄悄降级为逐段翻译。只重试失败阶段，兼容的成功初稿可在续跑时复用。

保持相同原文、模式、上下文及模型配置，才能复用待完成检查点。
切换模式不会重做已完成正式译文。命令及项目创建时的选择见
[CLI 指南](cli.md)和[配置参考](../reference/configuration.md)。

<a id="review-and-autofix"></a>

## Review 与 Autofix

Review 要求每章都已完成翻译。它用最终术语库检查连续原译文块，
可为不确定的问题取证、协调互相矛盾的建议，并提出修订。
额外轮次会重新检查修订后的文本，也会增加模型用量。

**`pipeline.review_autofix` 默认为 `true`，因此 Review 可以修改已保存译文。**
关闭 Autofix 后，新 Review 工作只生成建议，不将其发布到书籍中。

需要只获取建议、不开始发布时：

```bash
wenyi review book.epub --no-autofix
```

完整流程可设置 `pipeline.review_autofix: false`。
独立 Review 中，`--autofix` 可覆盖关闭的配置，强制发布。
**关闭 Autofix 阻止新发布，但已经开始、写入日志的发布会先恢复，
即使本次传入 `--no-autofix`，仍可能写回正式译文。**
该选项不是回滚命令，也不能取消已经提交的发布计划。

`pipeline.review: false` 或 `translate --no-review` 只跳过自动 Review。
显式 `wenyi review` 仍会执行。内容、术语、指导信息、语言策略及模型身份匹配时，
会复用完成结果或续跑未完成工作，**并非每次调用都新建 Review**。
这些输入变化时可能需要新一轮运行和新的模型费用。

Review 可能在轮次耗尽、仍有未解决问题、没有进展或出现修订循环时停止。
后续审校未再报告某问题，不证明替换内容正确。
准确性要求高的用途应先检查保存结果，再决定是否采用发布文本。

<a id="pause-and-resume"></a>

## 暂停与续跑

使用相同原文、目标语言和兼容配置重新运行。
CLI 状态按 `state/<book>/targets/<target-language>/` 隔离，
Web 和 Desktop 则保存各自独立的项目状态。同名但内容不同的文件不是同一份原文。

- 已完成正文批次保持保存；改变润色或翻译模式不会自动重做。
- 续跑可能先为已经翻译的批次补齐术语抽取，这不代表重新翻译该批次。
- 准备、精翻和 Review 复用身份匹配的成功检查点，不重复请求已完成模型阶段；
  没有持久成功记录的在途工作可能需要重新请求。
- 语言策略或提示词变化可能重建受影响的派生指导并产生模型用量，
  但保留已完成译文和术语。
- 翻译收尾可重试曾经失败的注释定位。因此，即使正文全部完成，
  再执行 `translate` 也不保证完全不调用模型。

用 `wenyi status` 查看保存进度，用 `wenyi inspect-run` 查看已记录的事件、用量及耗时。
累计 token 包括早先尝试和续跑，不只是最近一次命令。
恢复时保留状态与原文文件；需要完整重译或对比时，使用独立项目或状态目录。

<a id="re-export"></a>

## 不重译，只重新导出

`wenyi assemble` 从保存状态生成产物，**不调用翻译模型**。
更换格式、双语顺序或原文样式时使用它，
不会重新准备、润色、Review 或修复注释。

每次导出使用同一时点的已保存书籍快照。
另一个流程可以继续翻译；之后保存的新批次需要再次导出才能包含。
导出仍可能需要原始模板；PDF 还可能需要 BabelDOC 会话。
详见[导出快照](../reference/formats.md#export-snapshots)
及 [PDF 要求](../reference/formats.md#pdf)。

检查点所有权、发布日志、缓存身份与账本规则见
[开发者流程契约](../development/pipeline.md)。
