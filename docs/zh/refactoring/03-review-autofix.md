# 03 · 分离 Autofix 候选规划与索引发布

[总览](README.md) · [English](../../refactoring/03-review-autofix.md)

状态：待实施；高优先级，状态恢复风险高。基线：`7471256`。

## 证据

[`review_autofix.py`](../../../trans_novel/pipeline/review_autofix.py) 共 922 行。128 行的 `_run()` 长达 604 行，同时处理已有索引、推理身份、影子修改归一化、最终问题复核、并发修订、候选记录、位置汇总和发布；743 行的 `_apply_index()` 负责正式章节写入、对齐刷新与发布状态。

现有“先索引、后写正式译文”的设计应保留，通过重构明确规划与发布边界，不让 Review agent 直接发布译文。

## 建议模块与契约

| 模块 | 职责 |
| --- | --- |
| `review/autofix_models.py` | 纯 `AutofixRecord`、`PublishLocation`、`AutofixPlan` 类型与校验，编解码现有 JSON 结构。 |
| `pipeline/autofix_candidates.py` | 归一化影子修改，构造有效译文的不可变视图，对剩余问题分组、复核、修订，按原始位置合并。 |
| `pipeline/autofix_plan.py` | 把候选结果转成稳定记录与位置，计算哈希，保存规划身份和可恢复发布索引。 |
| `pipeline/autofix_publish.py` | 只应用已落盘的计划，校验正式译文，刷新依赖对齐并收尾发布记录。 |
| `pipeline/review_autofix.py` | `ReviewAutofixService` 选择最新相关 Review，路由续跑或规划，保留用量刷新范围。 |

发布器接收已校验计划、正式章节存储、Review 日志，以及明确的注释和 DOCX 对齐协作者；不接收候选 fixer，也不重新执行全书 Review。规划侧只接收不可变章节视图，不能保存正式章节。线程池留在候选执行侧，不放进门面或发布器。

## 发布契约

1. 新候选或模型调用前，先检查最新有效 Review 和已有索引；不能绕过新 Review 发布更旧的残留索引。
2. 保存并校验规划推理身份，保留模型变化后拒绝复用旧计划的现有行为。
3. 完整 `autofix/index.json` 先落盘，再改任何正式 target；保留记录 ID、位置顺序、修改前后文本及哈希。
4. 每个位置：当前文本等于索引目标则复用；等于索引原文且哈希匹配则应用；否则记录冲突或失败，不覆盖。
5. 保存章节文本、刷新未完成对齐、保存索引进展。任意相邻步骤间中断都必须可恢复。
6. 完成 completed/partial 结果并只合并一次用量，不新增段落历史字段，不修改 manifest 或术语库。

索引恢复会跳过候选生成和问题复核，但不能据此承诺所有续跑都没有模型调用：未完成的注释或 DOCX 混合样式对齐仍可能调用现有模型服务。测试和文档都要保留这一区别。

## 实施与验收

先拆计划类型和纯汇总，再原样提取发布器及顺序，随后提取候选执行，最后把 `_run()` 收敛为短协调器。按需复用 01–02 的类型，但不把发布并入影子审校引擎。

`tests/test_review_autofix.py` 已覆盖字段保留、最终复核、修订失败、待发布索引恢复和阻止发布旧索引。补充索引落盘后、章节落盘后、对齐中、结果落盘前的故障注入；每种场景续跑两次，正式译文、记录状态、对齐状态和用量应与完整运行一致。覆盖被外部改过的 target、同位置多条记录及成功失败混合情况。

运行 Autofix、注释、DOCX、计时、路由续跑和门面测试，再跑全量。关闭 Autofix 与待发布索引的当前路由行为先用测试固定；是否允许继续发布待处理工作属于另一个用户可见策略，不在移动代码时顺手改变。
